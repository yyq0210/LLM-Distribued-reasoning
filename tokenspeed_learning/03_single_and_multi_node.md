# 第三课 从单机双卡到两机双卡

前两课已经在一台机器的两张 GPU 上验证了通信。本课解释把两个进程放到不同机器后，有哪些变化，并提供启动模板。**当前没有第二个节点参与测试，因此本课没有跨机器的实测输出。**

[返回教程入口](README.md)。

## 1 先分清三个层次

| 层次 | 例子 | 负责什么 |
| --- | --- | --- |
| 模型如何分工 | 张量并行、流水线并行、专家并行 | 决定哪张卡计算什么、需要交换什么 |
| 通信操作与实现 | AllReduce、NCCL | 定义合并或交换规则，并实现数据传输 |
| 硬件连接 | NVLink、PCIe、网卡和网络 | 提供数据实际经过的通路 |

NCCL 是通信软件库，NVLink 是 GPU 互连技术，二者不在同一层。调用相同的 AllReduce，底层可以根据硬件和配置走不同路径。

本机安装验证时，两张 GPU 在 `nvidia-smi topo -m` 中的连接标记为 `NV18`，表示存在 NVLink 连接。拓扑信息描述硬件连接，不等于已经测得带宽，也不能仅凭它断定某次传输实际走了哪条路径。

## 2 单机和多机中编号怎样变化

继续采用“一进程一张 GPU”的课程配置。

| 部署 | 位置 | 全局 rank | local rank | world size |
| --- | --- | ---: | ---: | ---: |
| 单机双卡，已实测 | 机器 A 的第一张可见 GPU | 0 | 0 | 2 |
| 单机双卡，已实测 | 机器 A 的第二张可见 GPU | 1 | 1 | 2 |
| 两机各一卡，模板 | 机器 A 的第一张可见 GPU | 0 | 0 | 2 |
| 两机各一卡，模板 | 机器 B 的第一张可见 GPU | 1 | 0 | 2 |

多机时，`local_rank` 在每台机器内重新编号，所以两个进程都可以是 `local_rank=0`；全局 rank 仍然不同。

本课脚本要求总进程数恰好为 2。因此可以用一台机器两个进程，也可以用两台机器各一个进程，不能直接改成两机各两进程而不修改示例。

## 3 硬件通路有什么变化

单机 GPU 通信通常可以利用机内的 NVLink 或 PCIe。跨机器则需要可用的跨节点互连；常见部署通过网卡和网络完成，具体可能使用 RoCE、InfiniBand 或其他可用传输方式，不能假定所有集群都一样。

常见跨机通路可以理解为：

```text
机器 A 的 GPU → 机器 A 的网卡 → 网络 → 机器 B 的网卡 → 机器 B 的 GPU
```

这是帮助理解的示意。是否使用 GPU 直接访问网络、是否需要主机内存中转、带宽多大，都取决于实际硬件、驱动和 NCCL 配置，本次没有跨机验证。

**AllReduce 的数学结果不因部署位置改变。** 两个输入仍为 `[1, 2]`、`[3, 4]` 时，两个参与者都应得到 `[4, 6]`。这是由操作定义推导的预期结果，不是本次测出的多机日志。

## 4 两台机器如何启动

模板文件：[run_two_nodes.sh](run_two_nodes.sh)。两台机器都需要这份课程文件、兼容的学习环境和 GPU。模板通过相邻目录定位环境，因此复制代码时还需要相应准备另一台机器的环境，不能只复制一个 shell 文件。

下面的地址是占位符，执行前必须替换成机器 A 能被另一台机器访问的实际地址。两条命令需要在各自机器上及时启动；只启动一端会等待另一端。

机器 A：

```bash
cd /home/hadoop-scale-llm/dasc/tokenspeed_learning
bash run_two_nodes.sh 0 '<机器A可达IP>' 29500
```

机器 B：

```bash
cd /home/hadoop-scale-llm/dasc/tokenspeed_learning
bash run_two_nodes.sh 1 '<机器A可达IP>' 29500
```

| 参数 | 含义 |
| --- | --- |
| `0` 或 `1` | 当前机器的 node rank，两台机器必须不同 |
| 机器 A 的地址 | 两端约定的会合地址 |
| `29500` | 两端约定的会合端口，可改成双方一致且可用的端口 |
| `--nnodes=2` | 两台机器 |
| `--nproc-per-node=1` | 每台机器启动一个进程 |

会合地址让进程找到彼此，并不意味着全部 GPU 数据都通过这一个端口传输。NCCL 的数据通信还要能够建立相应网络连接。

第一课的 Python 数学计算无需改变：全局 rank 0 负责前半输入，全局 rank 1 负责后半输入，二者共同调用 AllReduce。变化主要在进程启动和底层传输路径。

## 5 遇到等待或报错先检查什么

| 现象 | 优先检查 |
| --- | --- |
| 启动后一直等待另一端 | 是否两台机器都已启动；node rank、地址、端口是否一致且正确 |
| CUDA 设备编号错误 | 每个进程的 local rank 是否对应本机可见 GPU；是否设置过 `CUDA_VISIBLE_DEVICES` |
| 到某个通信操作才卡住 | 两边是否按同样顺序调用；某个进程是否提前异常退出 |
| 数据形状相关错误 | 两边的形状、dtype 和拆分规则是否满足该操作要求 |
| NCCL 网络错误 | 先阅读双方日志，再检查实际网卡、路由和网络可达性 |

需要看 NCCL 诊断信息时，可以仅给本次启动添加 `NCCL_DEBUG=INFO`。例如在单机练习中：

```bash
cd /home/hadoop-scale-llm/dasc
NCCL_DEBUG=INFO bash tokenspeed_learning/run_lesson_01.sh
```

这是排查命令，不是已保存的性能测试。不要在不清楚网卡名称和拓扑时，直接照抄其他机器的网卡选择参数。

## 6 后续如何连接到大模型

理解前面的数字例子后，可以沿着三个问题继续读源码：

1. **张量并行 TP**：同一层分给多张 GPU，每张卡持有哪些权重，何时求和或拼接？先读第一课指向的 `RowParallelLinear`。
2. **流水线并行 PP**：不同层放在不同设备上，前一段的输出如何交给后一段？关注阶段间发送和接收。
3. **专家并行 EP**：不同专家放在不同设备上，token 如何按目标专家分发并返回？把第二课的按目的地交换作为起点。

TokenSpeed 的 [并行配置说明](https://github.com/lightseekorg/tokenspeed/blob/8289d0f4a9e122cec9ad7bc7bbb843fd9ade1613/docs/serving/parallelism.md) 可作为后续源码阅读入口。当前已完成独立通信操作和第四课线性层的双卡正确性练习，尚未运行完整模型的 TP、PP、EP 性能实验。
